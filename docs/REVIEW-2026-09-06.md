# Reliability and security review

## Scope and approach

Reviewed Discord commands/permissions, Armory parsing and scoring boundaries, metadata and summary caches, all card paths, Raid-Helper/forum discovery, role-based core comparison, private attendance/link stores, Windows launch/recovery scripts, the repository's weekly workflow, CI, dependencies, and operational documentation. Independent review passes were cross-checked before implementation. The result is a targeted refactor, not a new framework, database, or hosting migration.

Preserved GearScoreLite math, established GS tiers, source-sheet contents, event-selected readiness class/spec, intentional attendance states, officer-only ephemeral history, the card design, and three-times rendering resolution. No runtime dependency was added.

## Findings addressed

| Priority | Finding | Change and regression evidence |
| --- | --- | --- |
| High | Concurrent/truncated writes and catch-all reads could lose private state. | `JsonStore` serializes whole transactions, validates schemas, flushes a unique temporary file, atomically replaces the destination, and commits memory only after success. Tests cover cold concurrency, malformed files, write failure, and recovery. |
| High | Expired cached item values overrode fresh provider data; placeholder metadata could last a month. | Valid fresh fields take priority; display fallbacks stay separate; incomplete loads retry after one minute. Tests cover poisoned zero values, partial providers, duplicate fetches, disk errors, and restarts. |
| High | Discord async listener and error-response rejections escaped containment. | An outer acknowledgement-aware boundary contains handler/autocomplete/response failures. Roster paging and private persistence acknowledge before waiting. |
| Medium | Work and memory could accumulate behind serial browser operations. | One expensive operation per user, four total, bounded source caches, shared refreshes, and three concurrent event-discovery reads. This bounds load, not the total duration of a prolonged provider outage. |
| Medium | Explicit historical views could replace current defaults or compare old signups to today's core. | Current server-owned events alone can update defaults/history or expose core reminders. No retrospective reconstruction from current membership. |
| Medium | A send followed by a failed cooldown write could permit repeated pings. | Reserve the cooldown durably before the external send. Uncertain outcomes retain it and tell the officer to inspect the channel. |
| Medium | Old cached gear could certify current gem/enchant readiness. | Preserve its capture time, label stale fallback, and mark preparation unverified without mutating the cached audit. |
| Medium | Unicode roster names could exceed Discord component limits. | Compact Unicode button IDs with validation and legacy decoding compatibility. |
| Medium | Page creation failures could leak card/Armory contexts. | Shared card capture owns cleanup from page creation onward; Armory cookie/page setup is also inside cleanup. |
| Medium | Legacy boot migration could kill an unrelated shared process tree. | A live legacy PID now blocks migration; no generic tree-kill path remains in the installer. |
| Medium | GET transport failures were incorrectly rejected as uncertain mutations by the scheduler. | Provider errors retain HTTP method; only transient identified reads retry. Unknown mutation outcomes still require reconciliation. |

## Validation

- Baseline: type-check, 13 original bot test files, 157 weekly workflow tests, and dependency audit passed before changes.
- Refactor: type-check and all 21 automatically discovered bot test files passed; failure-oriented fixtures cover the changes above. All 167 weekly workflow tests passed. The dependency audit reported no known vulnerabilities.
- Visual smoke: `npm run test:cards` rendered synthetic fixtures for Armory, upgrade, readiness, attendance, and guild roster without Discord messages. All five PNGs are 2616 pixels wide; HTML escaping and closure of all five browser contexts passed. Outputs are ignored local artifacts, not public guild data.
- Read-only compatibility check: existing live private files parsed with the new validators; before/after hashes matched. No file conversion or data rewrite was required.
- Read-only integration check on September 6: forum discovery selected the September 12 02:00 UTC Pizza Core event, verified its server identity, and read all 25 current core-role members.
- A single fresh live Warmane summary returned 18 equipped items, a calculated GS, and a complete preparation audit using the refactored retrieval path. This is not an all-realms or full-raid load test.
- Hosted CI and runtime deployment must be verified for the final commit before describing it as deployed. Local validation does not prove an actual user invocation, restart, future scheduled delivery, or every supported realm.

## Remaining limits and operational boundaries

1. **One writer per data directory.** Transactions protect one process; they are not a cross-process lock or backup system. Host/disk failure still needs private backups.
2. **Upstream outages.** Warmane, Raid-Helper, Google Sheets, and icon hosts can throttle or fail. A cold full raid can still take time; admission limits do not guarantee completion before Discord's token expires during a sustained outage.
3. **Historical accuracy.** Existing snapshots are preserved, not retroactively corrected. Missing responses reflect the last captured snapshot, not proven in-game no-shows. Old weeks without an event-time core snapshot remain untracked.
4. **Retired PM2 helpers.** Legacy `.cmd`/`.js` recovery launchers can resurrect a whole PM2 daemon dump. They are not the current production task entrypoint and must not be re-enabled alongside Task Scheduler.
5. **Standalone manual publishing.** The manual `raid-helper-event.mjs apply` path does not have the weekly runner's durable mutex/create-intent journal. Do not invoke it concurrently for one raid occurrence; no publishing calls were made for this review.
6. **Separate installed scheduler.** Changes under `tools/pizza-raid-helper` are repository-source improvements only. The installed scheduler has a separate path/config/journal. A bot merge or restart does not deploy those files or justify a second schedule.
